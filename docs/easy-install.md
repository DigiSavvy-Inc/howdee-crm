# Easy install: the spec

This is the spec for epic #727, "viciously easy install". The build issues under that epic are
written to it. If a build has to differ, that PR updates this file and lists the change under
"Docs changes". The guide for installers is [self-hosting.md](self-hosting.md). It describes the
target flow, and each part that isn't built yet is marked "(planned, #n)".

Names in this file are placeholders. Replace `crm.example.com`, `howdee-crm` and
`<subdomain>.workers.dev` with your own.

## Goal

A new install takes one click or one command, then a few pages in the app:

- **Button path:** you sign in to Cloudflare once, type one phrase, and the app is live.
- **Terminal path:** you run `wrangler login` once, then one command, and you get a setup link.
- **Nothing to copy by hand:** no ids, no generated secrets and no config file edits on either path.
  Each install gets its own random secrets.
- **Existing installs keep working with no change.** An install that already has a filled-in
  `wrangler.jsonc`, secrets it set itself and the separate heartbeat Worker deploys exactly as
  before with `npm run deploy` (classic mode, [below](#classic-mode-an-existing-install-is-never-probed-or-changed)):
  nothing on its account is probed or changed.

## Decisions already made

- **Secrets are real Worker secrets.** The deploy script generates them and uploads them with the
  Worker (`wrangler deploy --secrets-file`, #730). They are never stored in D1.
- **One Worker runs the cron.** The app Worker gets a `scheduled` handler and a cron trigger of its
  own. The separate heartbeat Worker stays supported.
- **The button page asks for at most one value:** `SETUP_TOKEN`, a phrase the installer makes up.
  The terminal path asks for none.
- **The setup token has a minimum length (#747).** While no user exists, `/setup` refuses a
  `SETUP_TOKEN` shorter than 20 characters (after trimming): the page shows how to set a longer one
  (`npm run deploy -- --new-setup-token`, or changing the secret in the Cloudflare dashboard for a
  button install) and creates nothing. An install that already has an admin never reads
  `SETUP_TOKEN`, so it's unaffected whatever the value. A generated token is 32 characters.
- **A secret is never shown.** Generated values go to wrangler through a temporary file that is
  deleted afterwards. They are never printed, logged or committed. The one value an
  installer ever sees is the one-time setup link (terminal path).

## Path 1: the Deploy to Cloudflare button (files built, #732; account test pending)

| Step | What the installer does | Logins |
| --- | --- | --- |
| 1 | Clicks **Deploy to Cloudflare** in the README. | |
| 2 | Signs in to Cloudflare (or creates an account). | 1 |
| 3 | Connects a GitHub or GitLab account so Cloudflare can create a copy of the repository for Workers Builds. Skipped if one is already connected. | 0 or 1 |
| 4 | Keeps the suggested names for the Worker, the D1 database and the R2 bucket, or changes them. | |
| 5 | Types a phrase in the one field, `SETUP_TOKEN` (at least 20 characters), and keeps it for step 7. | |
| 6 | Clicks **Deploy** and waits for the build (a few minutes). | |
| 7 | Opens the Worker's URL, gets sent to `/setup`, types the phrase and creates the first admin. | |
| 8 | Follows the first-run wizard ([below](#first-run-wizard)). | |

**Logins: 1 (Cloudflare), plus 1 for GitHub or GitLab if none is connected yet.** The Postmark sign-in
needed to copy a server token comes later, in the wizard, and isn't part of the deploy.

The button is new and still being tested on a fresh account. The terminal path (`npm run deploy`,
Path 2) is the tested one.

This is what the build is designed to do: Cloudflare creates the D1 database and R2 bucket from the
config, and Workers Builds runs `npm run deploy` as the deploy command. That script does the rest
([what the deploy does](#what-the-deploy-does)). The phrase from step 5 is meant to be the only secret
the button page sets. The script generates the others on the first build.

**What the button reads (#732):**

- The button URL is `https://deploy.workers.cloudflare.com/?url=<public repository url>`, in the
  README and the self-hosting guide.
- `package.json` → `cloudflare.bindings`: one `description` each for `DB` (the D1 database),
  `MEDIA` (the R2 bucket) and `SETUP_TOKEN` (the one secret field).
- `.dev.vars.example`: the secret fields. It lists `SETUP_TOKEN` only. The full list of secrets the
  app reads, with a required / optional comment each, moved to `.dev.vars.reference`; local dev
  copies that one to `.dev.vars` (`wrangler types` reads secret names from `.dev.vars`), and so does CI.
- The `build` and `deploy` npm scripts: `deploy` is `node scripts/deploy.mjs`, which detects Workers
  Builds through `WORKERS_CI`.
- `worker-configuration.d.ts` is generated by `wrangler types` during the build. The public
  repository doesn't ship it, so `.gitignore` lists it (a fresh clone stays clean after a build).
  The private repository tracks it, and a tracked file isn't affected by `.gitignore`.

**The first tick.** Cloudflare can take up to 15 minutes to start a new Cron Trigger (8 minutes when
measured on a new account). Settings → Setup says so on its "Heartbeat" and "CRON_KEY" rows until the
first tick lands.

**Upgrading a button install.** The installer's repository copy is what Workers Builds deploys.
Bringing a release into it (GitHub's **Sync fork** when offered, else `git pull` from the public
repository and push) starts a build that runs `npm run deploy` again: migrations, then the upload;
secrets already set stay as they are. The copy may not be a fork, and git may refuse with unrelated
histories. Not tested yet. Written up in [self-hosting.md](self-hosting.md#upgrading).

## Path 2: the terminal (built, #730)

```sh
git clone <repository url> howdee-crm
cd howdee-crm
npm install
npx wrangler login
npm run deploy
```

| Step | What the installer does | Logins |
| --- | --- | --- |
| 1 | Clones the repository and runs `npm install`. | |
| 2 | Runs `npx wrangler login`, which opens a browser to sign in to Cloudflare. | 1 |
| 3 | Runs `npm run deploy`. No questions. | |
| 4 | Opens the setup link it prints at the end. | |
| 5 | Creates the first admin (the token is already filled in from the link) and follows the wizard. | |

**Logins: 1 (Cloudflare).**

The public repository ships a ready-to-use `wrangler.jsonc`, written by the public export from
`wrangler.example.jsonc` (`configFromTemplate` in `scripts/install-config.mjs`): default names
(Worker `howdee-crm`, D1 `howdee-crm`, R2 `howdee-crm-media`), no `database_id` and an empty
`PUBLIC_BASE_URL`. With no `wrangler.jsonc` at all, the script writes the same file; it never
overwrites one that exists. Change the names in it before the first deploy if you want others.

A login that reaches more than one Cloudflare account needs `CLOUDFLARE_ACCOUNT_ID` set first
(`export CLOUDFLARE_ACCOUNT_ID=<account id>`). The deploy captures wrangler's output, so wrangler has
no terminal to ask which account to use; it stops with one line saying to set the variable and lists
no accounts. `account_id` in `wrangler.jsonc` alone isn't enough: `wrangler r2 bucket list` doesn't
read the config.

The deploy writes the database id and the Worker's address into `wrangler.jsonc`. Neither is a
secret; commit them to your own copy or keep the change local.

## What the deploy does

`npm run deploy` (`scripts/deploy.mjs`, logic in `scripts/deploy-plan.mjs`, built #730) first picks a
mode from local files and flags only, before any network call, and prints one line saying which mode
and why.

### Classic mode: an existing install is never probed or changed

When `wrangler.jsonc` exists, has a real D1 `database_id`, there's no pending-install marker and no
`--setup` / `--new-setup-token` flag, the deploy is exactly the one before #730:

1. `wrangler d1 migrations apply <database_name> --remote` (the name from the `DB` binding, as
   before). A failed migration builds and uploads nothing.
2. `npm run build`
3. `wrangler deploy`

All three run interactively (inherited terminal). Nothing is listed (no `d1 list`, `r2 bucket
list`, `secret list` or user count), nothing is created, no secret is generated and no file is
written. A finished first install deploys this way from then on.

### Install mode

Install mode runs when any of these is true:

- `wrangler.jsonc` didn't exist (it's written from the template in this run, and never overwritten
  once it exists);
- its D1 `database_id` is missing, empty or the template's all-zero one;
- the pending-install marker `.wrangler/howdee-install.json` exists (below);
- `--setup` or `--new-setup-token` was passed (`npm run deploy -- --setup`).

Steps, in order. A failing step stops the run, and nothing after it runs. Each step says what it did
in one plain line ("Created database howdee-crm.", "Bucket howdee-crm-media found.", "Set 5
secrets: …", "Secrets: nothing to set.").

1. **Database.** `wrangler d1 list --json`.
   - A real `database_id` that's on the account → used. A real id that **isn't** on the account →
     stop with one line ("this database id is not on the logged-in Cloudflare account; check
     `wrangler whoami` or CLOUDFLARE_ACCOUNT_ID"). A real id is never replaced and no database is
     created in its place.
   - No id and no database with the name → `wrangler d1 create <name>`; the id is read from that
     command's own output (the config snippet it prints), else from the list, and written into
     `wrangler.jsonc`.
   - No id but a database with that name exists → used only when this install created it (the
     marker says so), inside Workers Builds (`WORKERS_CI` set: Cloudflare provisioned it from the
     config), or with `--adopt-database`. A bare `CI=1` doesn't adopt. Otherwise stop and name the
     database and the flag.
2. **Bucket.** `wrangler r2 bucket list` (text only; it has no JSON option, and it reads a single
   page from the API, so an account with very many buckets may not list them all). A listed bucket
   is used, except that a run creating its database never takes over a bucket it didn't make (stop:
   change `bucket_name`). Missing → `wrangler r2 bucket create <name>`. A create that fails with
   "already exists" stops: the name is taken or wasn't listed; pick another name. It's never taken
   as found.
3. **Migrations:** `wrangler d1 migrations apply <database_name> --remote`, interactive. A failed
   migration uploads nothing.
4. **Look up what's set.** `SELECT COUNT(*) FROM users` through `wrangler d1 execute <database_name>
   --remote --json` (read-only; a failure means "unknown", and no `SETUP_TOKEN` is generated), and
   `wrangler secret list --format json` for the names already set (names only, never values). Only
   wrangler's own `Worker "<name>" not found.` means a Worker that doesn't exist yet (no secrets);
   any other failure stops.
5. **Build:** `npm run build`.
6. **Upload with the missing secrets.** Each name in the table below that's missing gets a fresh
   value from `crypto.randomBytes`, written to a temporary JSON file (mode 0600, in a new folder in
   the system temp folder) and uploaded in the same version: `wrangler deploy --secrets-file
   <file>`. The folder is removed right after, and also on Ctrl-C, SIGTERM or an uncaught error. So
   a new install never runs without `SESSION_SECRET`. `--secrets-file` adds to the secrets already
   set and never removes one. Nothing missing → plain `wrangler deploy`.
7. **Print the setup link, right away.** When this run generated `SETUP_TOKEN` (no users yet), the
   link `https://howdee-crm.<subdomain>.workers.dev/setup#token=<SETUP_TOKEN>` is printed
   immediately after the upload, before any later step, so it can't be lost to a later failure.
   The token sits in the URL fragment, so it's never sent to the server or written to a log;
   `/setup` fills the field from it and removes it from the address bar.
8. **Fill in the address.** When `PUBLIC_BASE_URL` is empty (or still the template's
   `https://crm.example.com`), the workers.dev URL from the upload's output is written into
   `wrangler.jsonc` (the key is added if it's missing) and the Worker is uploaded once more
   (`wrangler deploy`, no build), so the built-in clock has an address (#729). A set
   `PUBLIC_BASE_URL` is never changed. A failure here only warns: the app is live, the marker stays
   and the next run finishes it.
9. **Closing line.**
   - This run generated the token: "Open the setup link above".
   - No admin, `SETUP_TOKEN` set but not by this run: open `/setup` and use the phrase you chose
     (at least 20 characters), or run `npm run deploy -- --new-setup-token` to get a fresh link.
   - No admin and no `SETUP_TOKEN` (CI): set it with `npx wrangler secret put SETUP_TOKEN` (at least
     20 characters).
   - The user count couldn't be read on what looks like a fresh install: open `/setup`.
   - An admin exists: the app's URL. The script doesn't read the database on a classic deploy, so it
     can't say whether `SETUP_TOKEN` is still needed; Settings → Setup does: once the first admin
     exists, its "First-run setup token" row says the secret can be deleted.

Every captured wrangler command runs with colour off (`NO_COLOR=1`, `FORCE_COLOR=0`), and ANSI codes
are stripped before its output is read. JSON output is used where the command offers it (`d1 list
--json`, `d1 execute --json`, `secret list --format json`).

**The pending-install marker** `.wrangler/howdee-install.json` (git-ignored, like all of
`.wrangler`) is written when a first install starts and deleted only when a run finishes fully. It
holds no secrets: the database and bucket names, which of them this install created, and the steps
done. With it, a first install that stopped half way resumes in install mode even though the
database id is already in `wrangler.jsonc`. `--setup` or `--new-setup-token` on an install that
already has its id leave no marker behind.

**Flags** (`npm run deploy -- <flag>`):

| Flag | Effect |
| --- | --- |
| `--setup` | Install mode on any install: checks the database and bucket, sets missing secrets. Changes nothing that exists. |
| `--adopt-database` | Use an existing same-named D1 database this install didn't create (outside Workers Builds). |
| `--new-setup-token` | While no user exists: generate a fresh `SETUP_TOKEN`, set it (the one replacement the deploy ever makes, and only for that name) and print the link. Refused when a user exists, when the user count can't be read, and in CI. Nothing is built or uploaded when it's refused. |

**When Cloudflare refuses a command** (no login, or a token without a permission), the script stops
with one line naming the command and the permission, for example `Cloudflare refused "wrangler d1
list --json": the API token needs the "Account · D1 · Edit" permission.` Only an API refusal
(an authentication error / code 10000, or a 403 from the Cloudflare API) is reported this way; a
local file error such as `EACCES` is shown as it is. R2 commands need "Account · Workers R2
Storage · Edit"; `wrangler secret` and `wrangler deploy` need "Account · Workers Scripts · Edit". It
runs with no prompts when `CI` or `WORKERS_CI` is set (classic mode keeps wrangler's own prompts).

### Generated secrets

| Secret | Value | Notes |
| --- | --- | --- |
| `SESSION_SECRET` | 32 random bytes, base64url | Changing it signs everyone out and breaks links in emails already sent, so it's never replaced. |
| `WEBHOOK_KEY` | 32 random bytes, hex | Goes in the Postmark webhook URL. The wizard shows that URL with the key masked and a Copy button (the one place the app hands it out, to an admin). |
| `CRON_KEY` | 32 random bytes, hex | Gates the HTTP tick and `/api/health`. The in-Worker cron doesn't need it. An install that keeps the heartbeat Worker sets the same value there. |
| `INGEST_KEY` | 32 random bytes, hex | Bearer key for `/api/ingest` and `/api/contacts/upsert`. Webhook keys in Settings → Webhooks work alongside it. |
| `MAIL_TOKEN_KEY` | 32 random bytes, base64url | Seals tokens entered in Settings. Replacing it would make them unreadable, so it's never replaced. |
| `SETUP_TOKEN` | 24 random bytes, base64url | Terminal path only, and only while no user exists. Never generated in CI. `--new-setup-token` makes a fresh one while no user exists. On the button path it's the installer's phrase, at least 20 characters (#747). It can be deleted once an admin exists (Settings → Setup says so). |

**A secret that's already set is never replaced,** whoever set it and whatever its value. Existing
values are never read. The script only checks which names exist (`wrangler secret list`). The one
exception is `--new-setup-token`, which replaces `SETUP_TOKEN` and only while no user exists.
There's no "rotate" flag. Rotation stays a manual `wrangler secret put`.

Not generated, because they come from someone else: `POSTMARK_TOKEN` (entered in Settings → Sending,
which already stores it sealed with `MAIL_TOKEN_KEY`), `POSTMARK_ACCOUNT_TOKEN`, `INBOUND_KEY` (made
when reply capture is turned on), `APP_PASSWORD`, the OAuth client ids and secrets, and the API keys
for AI and integrations.

## One Worker runs the cron (built, #729)

`npm run build` runs `scripts/wrap-worker.mjs` after `vite build`. It moves the adapter's
`_worker.js` to `_app.js` and writes a new `_worker.js` that exports the same `fetch` plus a
`scheduled` handler (`withClock` in `src/lib/server/internal-tick.ts`). wrangler's `main` is
unchanged. The handler runs one tick by calling the app's own `fetch` with an internal request to
`/api/automations/tick`, marked on the env object, so it needs no `CRON_KEY` and no network hop
(no error 1042). `wrangler.example.jsonc` has `"triggers": { "crons": ["* * * * *"] }`; without a
cron the handler never runs.

- **The HTTP endpoint stays.** `POST /api/automations/tick` with `CRON_KEY` works as before, for the
  heartbeat Worker, local dev and manual runs.
- **No public address, no tick.** The built-in tick uses Settings → Domain, else `PUBLIC_BASE_URL`,
  else the origin stored at `/setup` or chosen in the wizard (#731, below). Only with none of them does
  it run nothing, and Settings → Setup says why.
- **No sending credentials, no sends.** When the sending provider resolution finds no credentials
  (a fresh install before the wizard's Connect step), a tick on either clock skips every job that
  sends email: scheduled campaigns stay `scheduled` and unclaimed, best-time sends, resends and
  snapshot reports wait, automation email steps are held with "Finish setup: sending isn’t set up
  yet …" (re-checked every 10 minutes, retry attempts untouched), and a scheduled assistant job
  that delivers by email doesn't run at all (no model call, no run row, it stays due and runs once
  sending works); webhook-only jobs run as usual.
  Every housekeeping job (engagement, scoring, backups, pruning, syncs and the rest) still runs,
  `last_tick` is stamped, and the answer is a 200 with `skipped_sends: "no_sending_token"`, which the
  heartbeat Worker logs as ok. Settings → Setup shows a "Scheduled work" row until credentials are
  set. With credentials, the tick is unchanged. A saved token that can't be decrypted is not "no
  credentials": the tick answers 500, as before.
- **Held automation emails are bounded.** A pass held with "Finish setup" (no sender, or no sending
  provider) for 24 hours since its first such hold fails, like an email with no From did before #731,
  with `last_error` "No sender configured for 24 hours" or "No sending provider configured for 24
  hours". The clock is the first `held` timeline row of the current hold at that step (no migration).
  A send that already went out on an earlier tick is advanced, never held. While any pass is held,
  Settings → Setup shows an "Automation emails" row ("N automation emails are waiting: no sender
  configured").
- **Failures don't show in Cloudflare's cron history.** The handler never throws, so every run reads
  as a success there. A failed or skipped tick is in the Worker's logs and on Settings → Setup.
- **Ticks may overlap.** Sends and calls out claim their work, syncs hold leases and the daily jobs
  claim their run, so an install that runs both clocks does no harm, only extra work.
- **The tick time is shared.** Settings → Setup reads `app_state.last_tick` whichever clock wrote it.

**Moving an install with the heartbeat Worker over** (optional, at any time):

1. Add the `triggers` block to your `wrangler.jsonc` and run `npm run deploy`. Both clocks now run.
2. Check that Settings → Setup still shows a recent tick.
3. Delete the heartbeat Worker: `npx wrangler delete --name <your heartbeat name>`.
4. Keep `CRON_KEY`. It still gates `/api/health` and the HTTP tick.

An install that does nothing keeps the heartbeat Worker and works as before. `heartbeat/` stays in
the repository and stays documented.

## Vars become optional (built, #731)

Every var in `wrangler.example.jsonc` is either optional or set by the deploy. The ones the guide
calls required today get a stand-in:

| Var | Stand-in when empty |
| --- | --- |
| `POSTMARK_FROM` | Settings → General → Default From. The wizard asks for it. Until then, sends are refused with "Finish setup: no sender configured. Set the Default From address in Settings → General (or follow Settings → Setup)." An automation email step saved with no From of its own sends from the Default From, else `POSTMARK_FROM`; with neither, the pass is held at that step with that message (not failed, up to 24 hours, above) and sends once a sender exists. Reply forwarding, its self-loop guard and the compose test recipient use `POSTMARK_FROM` when set, else the Default From. A value with a display name (`Brand <a@example.com>`) counts as its bare address for the self-loop guard and the sending domain; before #731 it never matched. |
| `POSTMARK_STREAM` | Settings → Sending stream name, else `broadcast`. |
| `POSTMARK_STREAM_TX` | Settings → Sending stream name, else `outbound`. |
| `PUBLIC_BASE_URL` | Settings → Domain, else the origin of the first admin's `/setup` request, stored in `app_state` (`public_base_url_seen`), else the current request's origin. Background jobs (the tick) use the stored value, so links in automation emails are right before a custom domain exists. Only the request's own URL is stored, never a header; the internal tick origin, `.invalid` hosts, loopback hosts and plain `http` are refused. No page load ever writes it. An install with no stored value (set up before #731, or on `localhost`) keeps following the request origin until an admin chooses **Use this address for links** in the wizard's first step. |
| `WORKER_NAME` | The script fills it in from `name` (planned, #727). Empty = Settings → Domain "Attach" reports "Not configured", as today. `CF_ACCOUNT_ID` is the same: only "Attach" needs it. |
| Provider token | Settings → Sending or the wizard (sealed with `MAIL_TOKEN_KEY`), else `POSTMARK_TOKEN`. Until one is set, a send is refused with "Finish setup: sending isn’t set up yet. Paste the sending provider’s token in Settings → Sending (or follow Settings → Setup)." instead of a 500: as the form's own error line in Compose (send, schedule, 1:1, test), a campaign's resend, an automation step's test and the conversation / contact page reply box, and as a 409 JSON answer from an API route. A tick skips its sends (above). |

The other vars (`DEFAULT_LIST_NAME`, `REVIEW_FROM`, `REVIEW_TO`, `POSTMARK_INBOUND_ADDRESS`,
`INBOUND_FORWARD_TO`, `CF_ACCOUNT_ID`, `ARCHIVE_ROUTE_HOSTS`) are optional already. A var that's set
always wins over its stand-in, so a filled-in `wrangler.jsonc` behaves as before. One deliberate
change for existing installs: a new automation step's default From is now the Default From, then
`POSTMARK_FROM` (it was `POSTMARK_FROM` only), matching the builder.

## First-run wizard (built, #731)

After `/setup` creates the first admin, the app opens **Settings → Setup** with `?first=1` as a
wizard (`?wizard=<step>` opens one step; **Open the setup wizard** on the page brings it back). Each
step can be skipped and finished later. The checklist below stays the source of truth.

1. **Create the first admin** (built, #606): token, name, email and password, plus an optional GitHub
   login. The setup link's `#token=` fills in the token (the page's script reads the fragment, then
   removes it from the address bar); a typed token works as before, with the same lockout.
2. **Your address:** which address links use and where it comes from (Settings → Domain,
   `PUBLIC_BASE_URL`, recorded at setup, or this request), shown plainly by host. While neither
   Settings → Domain nor `PUBLIC_BASE_URL` is set and this page is open on another valid address
   than the recorded one (or none is recorded), **Use this address for links** records this
   request's origin; **Clear the recorded address** forgets it (both refused while Settings →
   Domain or `PUBLIC_BASE_URL` decides the links). A host shaped like a Cloudflare
   version preview (`<8 hex>-<name>.<subdomain>.workers.dev`) gets a note, but isn't refused: an
   ordinary Worker can have such a name. Then the Default From address.
3. **Connect sending:** pick the provider and paste its token (stored like Settings → Sending), then
   the connection is tested; nothing is sent. The stream names shown are the ones in effect
   (`broadcast` / `outbound` unless Settings → Sending names others); the wizard doesn't create
   streams. Only Postmark can be picked until the other adapters ship
   ([sending-providers.md](sending-providers.md)).
4. **Postmark webhook:** shows `<base>/api/webhook?key=••••••••`. **Create the webhook** lists the
   broadcast stream's webhooks (`GET /webhooks`). One pointing at this install's address with its key
   is "Already set up". One with this install's key on another host "points at another address", and
   **Update** moves it here (`PUT /webhooks/{id}`, the URL only). With none, it creates one
   (`POST /webhooks`, a trigger for each event `/api/webhook` reads: Open, Click, Delivery, Bounce,
   SpamComplaint, SubscriptionChange). It reports the stream and its unsubscribe handling, with
   **Switch to custom**. Postmark's error messages are shown with the token and the key replaced by
   dots. **Show the URL to copy** returns the full URL to an admin on request; the page data never
   carries the key.
5. **Send yourself a test** to the admin's email, on the transactional stream.
6. **Done:** the optional parts (reply capture, custom domain, GitHub sign-in, Gmail, AI and the
   rest) that are still off, each linking to its page.

## Out of scope

- Hosted instances and the fleet tooling. They're separate and private, and none of their code moves
  into public files.
- Creating the Postmark server, its streams or DNS records for the installer. The wizard checks,
  links and explains them, but doesn't create them.
- Custom domains during install. Settings → Domain covers them afterwards.
- Another way to keep secrets (D1, KV) and automatic secret rotation.
- Installing the optional integrations (GitHub OAuth, Google, AI keys) from the deploy.
- Removing the heartbeat Worker or the HTTP tick.
- Other hosts than Cloudflare.

## Open questions

To settle before the build issues start. Each answer goes into this file.

1. **Workers Builds token permissions.** The button path runs `npm run deploy` inside Workers Builds.
   Does its default API token allow `wrangler d1 migrations apply --remote`, `wrangler secret list`
   and `wrangler secret put`? If not, which permissions must the installer add, and can the button
   path get by without that extra step (for example by moving secret generation to the first request)?
2. **Resource ids in the config.** Does the button need `database_id` and `bucket_name` in the
   committed `wrangler.jsonc`, or does automatic provisioning create them from names alone? Related:
   the public repository ships only `wrangler.example.jsonc`, but the button reads `wrangler.jsonc`.
   Does the public export start shipping a `wrangler.jsonc` with no ids (and the export scan allow
   it), or does the button point at the example file some other way?
3. **Blank secrets on the button page.** The button page lists the names in `.dev.vars.example` as
   fields. Can a field be left blank, so that only `SETUP_TOKEN` needs a value? Or must
   `.dev.vars.example` shrink to `SETUP_TOKEN` alone, and the full list move to another file for

### Answers (#730)

1. Not known yet; to be tested with the button on a new account (#732). Until then, a refused command
   stops the deploy with one line naming the command and the permission it needs.
2. The public export writes `wrangler.jsonc` from the template, with names and no ids. The terminal
   path writes the same file when it's missing and never overwrites one.
3. `.dev.vars.example` lists `SETUP_TOKEN` alone, so the page has one field; the full list moved to
   `.dev.vars.reference` (#732). Whether the page accepts a blank field wasn't needed in the end.
4. Secrets go up with the first upload: `wrangler deploy --secrets-file <temp file>`, deleted
   afterwards. There's no window without `SESSION_SECRET`.
5. Yes: the script creates the database explicitly (`wrangler d1 create`) when the config has no id,
   on both paths. A real id that isn't on the account stops the deploy instead (no replacement is
   created). Inside Workers Builds (`WORKERS_CI`), a database with the config's name and no id in
   the config is taken as already provisioned and nothing is created; elsewhere that needs
   `--adopt-database`.
